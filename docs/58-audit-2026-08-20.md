# Audit round 5 (Aug 20, 2026): docs/53 run again, focused on Saved Words

Same playbook as [56-audit-2026-08-16.md](56-audit-2026-08-16.md) —
[53-comprehensive-audit-prompt-playbook.md](53-comprehensive-audit-prompt-playbook.md), run
deliberately as-is again (its own Project Context, its own A-F agent split, its own P0-P4 scale),
six parallel read-only agents. Every agent was told to read docs/40-45, docs/50, docs/52, and
docs/56 first so nothing already-fixed gets re-reported, and to give the newest code — the Saved
Words feature (docs/57, shipped across PRs #48/#49/#50) — extra scrutiny, since it's the least
audited code in the repo and shipped fast (three follow-up fix PRs in quick succession after v1).

**Net result: 21 new findings. Two P1, five P2, seven P3, seven P4. Zero P0.** No data loss or
security-critical issue found, but two of the P1s are real, deterministic, user-facing bugs — one
of them (58-1) undoes part of the point of the most recent placement-rule revision (docs/57 §1,
fixed in PR #49): the plus icon is now reachable mid-quiz, but tapping it can silently jump the
quiz to a different question and wipe whatever the player had typed.

**Status: the two P1s fixed** (same-day follow-up, on request). 58-18 also got fixed as a direct
side effect of 58-2's fix (see its entry below). Everything P2 and below is still open.

## Executive summary

- **Health:** still good outside the newest surface. Four separate agents (A, D, E, F) re-verified
  the pre-existing codebase (quiz-runner state machines, API ownership checks, migration-vs-schema
  fidelity, nav/docs consistency) and found nothing new — every regression this round is confined
  to the Saved Words feature added since docs/56.
- **Biggest strength this round exposed:** the new feature's *backend* is solid — Agent D traced
  every mutating route's race-safety, ownership checks, and migration-SQL-vs-schema fidelity in
  detail and found zero bugs, only documentation gaps. The three-agent-independent-convergence on
  finding 58-2 (see below) is itself a signal the review process is working as intended.
- **Biggest risk:** two P1s, both in the client. **58-1** is a real interaction bug: any word row
  inside an in-progress quiz is itself a click target (`goTo(index)`), and neither the new plus
  icon nor the pre-existing speaker icon stops that click from bubbling — tapping either mid-quiz
  can jump to a different question and clear the player's typed answer. **58-2** is a state-sync
  bug three agents (A, B, F) independently converged on: `SavedWordsProvider`'s `useState` doesn't
  resync when `router.refresh()` re-renders `RootLayout` with new `initial` props, so turning
  Saved Words on/off (or removing a word) doesn't actually propagate anywhere else in the app
  without a full hard reload — including on `/saved-words`'s own page.
- **Launch readiness:** nothing here is a security hole or data-loss risk; the two P1s are UX
  correctness bugs worth fixing before calling Saved Words done, not blockers on anything else in
  the app.

## Findings by area

### Bugs & reliability (Agent B) / UI-UX (Agent C) — the two P1s

**58-1. ✅ Fixed. Clicking the plus icon (or the pre-existing speaker icon) inside an in-progress
quiz can jump the quiz and wipe the typed answer — P1.**
`src/components/quiz/QuizRunner.tsx` (word row `onClick={() => started && goTo(index)}`, `~L377`;
`SaveWordButton`/`SpeakerButton` nested inside at `~L411-412`), `src/components/quiz/
ChoiceQuizRunner.tsx` (same pattern, row `~L358`, buttons `~L384-385`). Once a quiz is `started`,
every word row doubles as a nav target — clicking it calls `goTo(index)`, which changes the
current question and clears the typed input (`QuizRunner.tsx` `goTo()`, `L167-171`). Neither
`SaveWordButton` nor `SpeakerButton` (nor the row markup) calls `stopPropagation()`, so a tap on
either nested button also fires the row's own click handler. Concretely: mid-quiz, tapping the
plus icon on any row other than the current question jumps you there and discards what you'd
typed for the question you were actually answering. `SpeakerButton` had this latent bug before
Saved Words existed, but the plus icon doubles the surface and is a much more likely thing to tap
mid-answer — directly undercutting the whole point of PR #49's placement-rule revision (saving a
word *during* a quiz without disrupting it). Fix: `e.stopPropagation()` inside both buttons' own
`onClick` handlers (fixes every current and future call site in one place), or wrap the containing
`<span>` at each row. Confidence: confirmed (deterministic DOM bubbling, verified no
`stopPropagation` exists anywhere in either component).
**Fixed, with a scope change beyond the recommendation above (on request):** added
`e.stopPropagation()` inside `SaveWordButton`'s own `onClick` (`src/components/SaveWordButton.tsx`)
— covers every call site in one place, as suggested. But `SpeakerButton` was **removed from every
in-quiz context entirely** (`QuizRunner.tsx`, `ChoiceQuizRunner.tsx` — now `{!started && ...}`;
`CharacterQuizRunner.tsx` — dropped from both in-quiz cards outright, it had no pre-start version
to fall back to) rather than just having its own click guarded. Reasoning: playing a word's
pronunciation mid-quiz literally speaks its pinyin out loud — in Type Pinyin mode (and Character
mode's pinyin-typing format) that's the exact answer being tested, a real answer leak
`stopPropagation` alone wouldn't have addressed. The plus icon carries no equivalent risk (its
toast only ever names the Chinese character, never pinyin/meaning — confirmed unchanged, and now
documented with an explicit comment in `context.tsx`) so it keeps working in-quiz. Verified live:
started a quiz, typed a partial answer, saved a *different* row's word — current question and
typed text were both unchanged, and the speaker icon is gone from every in-quiz row/card while
still present on every pre-start table.

**58-2. ✅ Fixed. `SavedWordsProvider`'s state never resyncs after `router.refresh()` — toggling
Saved Words on/off doesn't propagate without a hard reload — P1.**
`src/lib/saved-words/context.tsx:29-36` (`useState(initial.enabled)`,
`useState(() => new Map(initial.saved...))`), seeded once in `src/app/layout.tsx:80-92`, consumed
by `src/components/saved-words/SavedWordsToggle.tsx:17-28`. Independently reported by three
agents (A, B, F). A `useState` initializer only runs on first mount; `SavedWordsProvider` sits at
a stable position in the tree with no `key`, so a later re-render with new `initial` props (which
`router.refresh()` does produce, since `RootLayout` re-executes) is silently ignored — verified
against this repo's own installed Next.js docs (`node_modules/next/dist/docs/.../use-router.md`),
which state a soft refresh explicitly preserves existing Client Component state. Concretely: a
new user's very first flow — visit `/saved-words`, click "Turn on Saved Words" — leaves every
plus/check icon invisible everywhere, *including on `/saved-words`'s own word table*, until a full
browser reload (F5), not just a client-side navigation. Turning it off has the mirror bug: plus
icons keep showing for the rest of the session. Fix: expose a re-seed/setter from the context and
call it from `SavedWordsToggle`'s success handler instead of relying on `router.refresh()` to
touch unrelated client state, or key `SavedWordsProvider` on something that changes across the
toggle so it deliberately remounts. Confidence: confirmed.
**Fixed** exactly as recommended: `SavedWordsContext` now exposes `setEnabled`
(`src/lib/saved-words/context.tsx`); `SavedWordsToggle` reads the server's confirmed `{ enabled }`
from the toggle POST's response and calls it directly, instead of trusting `router.refresh()` to
reach this context. `router.refresh()` is kept alongside it — still needed for `/saved-words`'s
own server-rendered content (`page.tsx` reads the flag server-side to decide whether to render the
off-screen or the word list). Fixing this required reading the POST response, which also fixed
**58-18** (`res.ok` is now checked) as a direct side effect, not a separate change. Verified live:
toggled off, then used a client-side nav link (no reload) to a chapter page — plus icon correctly
gone; toggled back on, same client-side navigation — plus icon appeared immediately.

### Bugs & reliability (Agent B) — remaining findings

**58-3. `SavedWordsPanel.remove()` unconditionally remounts the in-progress quiz — P2.**
`src/components/saved-words/SavedWordsPanel.tsx:31-39` (`remove()`), `:66-73`
(`<QuizModeGate key={quizKey} .../>`). The word table and the quiz panel are both mounted at once
on `/saved-words` — nothing hides the table while a quiz is running. `remove()` bumps `quizKey`
after *any* successful deletion, forcing a full `QuizModeGate` remount regardless of whether the
removed word has anything to do with the active quiz. A player who starts a drill, then removes an
unrelated saved word from the table below, loses their in-progress run (score, current question,
timer) with no warning. Fix: only reset when the removal actually affects the active quiz's word
set (or simplest: disable Remove controls while a quiz is in progress). Confidence: confirmed.

**58-4 (folds Agent F's independent finding of the same root cause). `SavedWordsPanel.remove()`
only updates local component state, not the shared `SavedWordsContext` — a removed word can't be
re-saved elsewhere in the same session without a hard reload — P2.**
`src/components/saved-words/SavedWordsPanel.tsx:31-39`; `src/lib/saved-words/context.tsx` exposes
no `unsave`. After removing a word on `/saved-words`, the shared `saved` Map every `SaveWordButton`
elsewhere reads from still has it — clicking + for that word on a chapter page or in a quiz just
shows "Already saved." and doesn't even hit the network (`context.tsx` `save()`, `L42-45` short-
circuits on `saved.has(...)`), so it silently can't be re-saved until a hard reload. Fix: add
`unsave(chinese)` to the context (DELETE + update the shared Map), have `SavedWordsPanel.remove`
call it instead of a bare `fetch`. Confidence: confirmed.

**58-5. Toast's Undo silently desyncs client/server state on delete failure — P3.**
`src/lib/saved-words/context.tsx:69-76`. Undo removes the word from local state *before* the
`DELETE` resolves, and swallows any failure (`.catch(() => {})`) with no rollback and no error
toast. On a failed/slow delete, the UI shows the word as unsaved while the server-side row still
exists, with no way for the player to discover the desync short of clicking + again later and
getting a confusing "Already saved." for a word the UI just told them was removed. Fix: await the
delete before mutating local state, or roll back + show a failure toast on error, mirroring the
existing pattern in `save()`. Confidence: confirmed.

**58-6. `SaveWordButton` has no in-flight guard — rapid double-click can produce a contradictory
toast pair — P4.**
`src/components/SaveWordButton.tsx:29-31` (no disabled state during the request);
`src/lib/saved-words/context.tsx:42` (`saved.has(...)` checked against state captured at click
time). Two fast clicks before the first request resolves both read the same not-yet-saved state
and both POST. The server handles this correctly (pre-check + `P2002` catch-and-recheck, no
duplicate row), but the player sees "Saved 你." immediately followed by "Already saved." stacking
on top — reads as a bug even though the data is fine. Fix: disable the button while its own
request is in flight. Confidence: likely.

**58-7. `SavedWordsPanel.remove()` fails silently on a non-OK response — P4.**
`src/components/saved-words/SavedWordsPanel.tsx:31-39`. If the `DELETE` returns non-OK, the row
correctly stays in the list (no false state), but there's no toast or any other feedback that the
click did nothing. Fix: show a toast on failure, matching `save()`'s existing pattern. Confidence:
confirmed.

### UI/UX, accessibility & responsive (Agent C) — remaining findings

**58-8. Toast becomes keyboard-unreachable when triggered from inside `CharacterBrowse`'s
focus-trapped dialog — P2.**
`src/components/quiz/CharacterBrowse.tsx` (dialog `L131-153`, uses `useFocusTrap`);
`src/lib/use-focus-trap.ts` (Tab-wrap logic); `src/components/toast/ToastProvider.tsx` (portals to
`document.body`, `L51-59`). The focus trap intentionally keeps Tab cycling inside the dialog's own
boundary (that's the point of docs/56 finding 56-8) — but a toast fired by saving a word from
inside that dialog portals outside the trap, so a keyboard-only user can never Tab to its Undo or
X; it just auto-dismisses 4.5s later. Mouse users are unaffected. Undo is the toast's headline
feature (docs/57 §7) — for this one call site, keyboard users can't use it at all: a real WCAG
2.1.1 gap on the first toast this codebase has shipped. Fix: don't trap focus while an
action-bearing toast is visible, or move focus to the toast's action when one fires during an
active trap. Confidence: confirmed.

**58-9. Toast's "Undo" link text fails WCAG AA contrast and violates this repo's own
accent-usage rule — P2.**
`src/components/toast/ToastProvider.tsx:87` (`text-accent hover:text-accent-hover`). `--accent`
(`#c1442d`) on `--surface` (`#212124`) computes to **~3.16:1** — below AA's 4.5:1 for normal
14px/`font-semibold` text (not large enough to qualify for the 3:1 large-text threshold). Also
directly contradicts `docs/10-color-palette.md`'s explicit rule: *"[--accent] never colors body
text, links, secondary buttons, or decoration."* Same class of bug docs/56 (finding 56-2) already
fixed for three other tokens — this is a fresh instance, introduced by new code, on a token that
was previously never used as small interactive text anywhere in the app. Fix: swap to
`--accent-secondary` (already brightened past AA per docs/56/docs/10) or `--foreground` +
underline. Confidence: confirmed (contrast math verified; grep-confirmed no other small-text usage
of `--accent` exists to be consistent with).

**58-10. Toast live region may not reliably announce to screen readers — P3.**
`src/components/toast/ToastProvider.tsx`, `ToastItem` (`L64-102`) mounts a brand-new
`role="status"` element with its full text in the same paint, then unmounts it entirely on
dismiss, rather than updating a single persistent live region. This is a well-documented ARIA
gotcha — some browser/AT combinations are inconsistent about announcing a region whose role and
content both appear simultaneously for the first time. As the first live region this codebase has
shipped, there's no established precedent to lean on, and it hasn't been verified with a real
screen reader. Fix: mount one persistent live-region container in `ToastProvider`, update its text
per toast instead of creating/destroying a role-bearing element each time; spot-check with a real
AT before treating this as settled. Confidence: likely (mechanism is well-documented; actual
impact is AT/browser-version dependent).

### Security & performance (Agent E)

**58-11. No rate limiting on any of the 3 Saved Words API routes — P2.**
`src/app/api/saved-words/route.ts` (POST), `src/app/api/saved-words/[id]/route.ts` (DELETE),
`src/app/api/account/saved-words-toggle/route.ts` (POST). None call `checkRateLimit` from
`src/lib/api-rate-limit.ts`. `src/app/api/attempts/route.ts` was specifically patched for exactly
this risk (per its own comment, citing docs/41) — a logged-in user could script unlimited writes.
The same risk applies here: unlimited `SavedWord` creates, unlimited toggle transactions, unlimited
deletes, each a real DB round trip against the shared Neon instance. Fix: add
`checkRateLimit` at the top of each handler, same shape as `attempts/route.ts`. Confidence:
confirmed (grep for `checkRateLimit` across `src/app/api` found only `attempts` and the cron purge
route).

**58-12. `POST /api/saved-words` accepts unbounded-length strings — P3.**
`src/app/api/saved-words/route.ts:22-27`. `chinese`/`pinyin` are only checked non-empty after
`.trim()`; `meaning` isn't even trimmed, and none have a max-length check. `SavedWord`'s schema
columns are plain Postgres `text`, unbounded. The legitimate UI flow never sends oversized values,
but the route itself trusts the raw JSON body from any authenticated caller (curl/devtools) — combined
with 58-11's missing rate limit, this is a genuine unbounded-storage-growth vector at negligible
cost to the caller. Fix: cap `chinese`/`pinyin` (~100 chars) and `meaning` (~500 chars), trim
`meaning` too, reject oversized payloads with 400. Confidence: confirmed.

**58-13. Redundant, uncached session/flag queries stack up further with each new feature — P3.**
`src/app/layout.tsx:80-83`, `src/components/layout/AppHeader.tsx:11`,
`src/app/saved-words/page.tsx:8-9`, `src/lib/auth/auth.ts:152-166` (`getSessionUser`, not wrapped
in React's `cache()`, and `session.cookieCache` isn't configured). `getSessionUser()` is a real DB
read, called independently in `RootLayout`, again inside `AppHeader` (a child `RootLayout`
renders), and a third time via `requireSession()` on `/saved-words` — three un-deduped session
lookups for one request. On top of that, `/saved-words` calls `getSavedWordsEnabled(user.id)`,
re-fetching the exact flag `RootLayout`'s new `getSavedWordsInitialState` already fetched one level
up in the same request. Not introduced by Saved Words (the `AppHeader`/`RootLayout` duplication
pre-dates it), but the feature adds two more calls on top of an already-unaddressed pattern instead
of working around it. `getSavedWordsInitialState` itself is efficient in isolation (one Prisma
call, no N+1) — the finding is about the stacking, not that one query. Fix: wrap `getSessionUser`
in React's `cache()` (one-line change, no call-site changes, retroactively fixes the pre-existing
duplication too); have `/saved-words` read `enabled` from the context `RootLayout` already seeds
instead of re-querying. Confidence: confirmed.

## What's already good / don't touch

- **The backend is genuinely solid.** Every mutating Saved Words route checks session + ownership
  before touching data, matching the established `friends/**` pattern exactly; the POST route's
  pre-check-then-`P2002`-catch upsert correctly handles the real concurrent-save race without
  needing transaction overhead (every write is scoped to one user's own row, so there's no
