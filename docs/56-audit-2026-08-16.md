## Findings by area

### Bugs & reliability (Agent B)

**1. ✅ Fixed.** **Friend-request creation race can produce two mirrored pending rows, letting an
"ignore" get silently overridden — P2.**
`src/app/api/friends/requests/route.ts:30-62`, `prisma/schema.prisma:187-203`. The dedup check is
a classic check-then-act TOCTOU (`findFirst` for an existing row between the two users, then
`create` if none found), and the schema's only constraint (`@@unique([userId, friendId])`) is
directional, not symmetric — nothing stops `(A,B,pending)` and `(B,A,pending)` coexisting if A and
B send each other a request in the same race window. If B then ignores A's request, only the A→B
row flips to `"ignored"`; the mirror B→A row stays pending, and A can accept it anyway — the
ignore doesn't stick. Distinct from the already-known, harmless accept/ignore race on a *single*
row (docs/41/52) — this one produces two independent rows that can resolve to contradictory
outcomes. Fix: wrap create in a `$transaction` with serializable isolation, or better, enforce
symmetry at the DB level (canonical-pair unique index). Confidence: likely.
**Fixed**: wrapped the check+create/update in a `prisma.$transaction` at Serializable isolation,
with a retry loop (up to 3 attempts) for the expected P2034 serialization-conflict error that
isolation level produces under real contention.

**10. ✅ Fixed.** **`CustomQuizPicker`'s load/persist effects transiently write `{}` to
localStorage on mount, self-correcting same-tick — P4.**
`src/components/quiz/CustomQuizPicker.tsx:106-115`. Real effect-ordering quirk, near-zero
real-world reachability (would need an interrupted page-unload in a sub-millisecond window).
**Fixed**: added the `hydratedRef` guard the finding suggested.

### UI/UX, accessibility & responsive (Agent C)

**2. ✅ Fixed.** **`--danger`/`--accent-secondary`/`--success` fail WCAG AA contrast as body text — P2.**
`src/app/globals.css:12-28`, used across every auth form's error text, quiz results'
missed/save-failed messages, and the Custom Quiz Picker's success badge. Computed real contrast
ratios (not visual guess) from the actual token hex values: `--danger` on `--background` =
**3.23:1**, on `--surface` = **2.93:1**; `--accent-secondary` on `--background` = **3.63:1**;
`--success` on its own badge surface = **3.65:1**. AA requires 4.5:1 for normal-weight text at
this size. All four fail by 20-35%, while `--foreground` (14.4:1) and `--muted-foreground` (6.3:1)
both pass comfortably — this isn't a systemic dark-theme problem, just these four tokens. `--danger`
specifically is the color used for login/registration/reset-password error text — exactly where
legibility matters most. Fix: brighten the three tokens a few percent luminance, re-verify against
a contrast checker; `--accent` itself needs no change (its real usages all qualify as WCAG "large
text," which only needs 3:1). Confidence: confirmed. **Fixed**: `--danger` → `#e06757` (5.3:1 vs
`--background`, 4.8:1 vs `--surface`), `--accent-secondary` → `#aa834c`, `--success` → `#7aa870`
— all computed to clear 4.5:1 against their real usage backgrounds; docs/10 updated with the same
computed ratios.

**3. ✅ Fixed.** **Custom focus indicators on text inputs and the Custom Quiz Picker's checkbox
composite to ~1.9:1, well under the ~3:1 a focus indicator needs — P2.** Every auth/friend-request text input
plus both typing-mode quiz runners' pinyin field use `outline-none focus:border-border-strong`,
stripping the native outline and replacing it with `--border-strong`
(`rgba(239,231,218,0.22)`), which composites to **1.87-1.90:1** against the surfaces it sits on.
The Custom Quiz Picker's checkbox (a hidden real `<input>` + styled `<span>`) has the same issue
via `peer-focus-visible:ring-border-strong`. No global `focus-visible` fallback exists anywhere in
`globals.css`, so once the outline is suppressed there's no other visible cue — affecting the
primary interaction surface of the whole site (the pinyin input) for keyboard users. Buttons/links
elsewhere don't override `outline-none` and are unaffected. Fix: either stop suppressing the
native outline, or swap `--border-strong` for something that composites to ≥3:1 on focus.
Confidence: confirmed. **Fixed**: added a new `--focus-ring: rgba(239, 231, 218, 0.4)` token
(~3.3:1 vs `--surface`) scoped specifically to focus-visible state, and swapped every
`focus:border-border-strong`/`peer-focus-visible:ring-border-strong` usage to it —
`--border-strong` itself left unchanged for its other role (hover border).

**8. ✅ Fixed.** **No Tab-key focus trap in `LogoutButton`/`CharacterBrowse` dialogs — P3,
re-confirmed unchanged (until now).** Was tracked as an open finding since docs/52. **Fixed**: a
shared `useFocusTrap` hook (`src/lib/use-focus-trap.ts`) cycling Tab/Shift+Tab between each
dialog's first/last focusable elements, wired into both.

### Backend/API & data integrity (Agent D)

**4. ✅ Fixed.** **`prisma/seed.ts`'s dialog-transcript reseed isn't transactional — P2.** `prisma/seed.ts:
252-264`. `seedTranscripts` does `deleteMany` then `createMany` for a chapter's `DialogLine` rows
as two separate unguarded awaits, unlike every other stale-row cleanup in the same file (which
upsert current data *first*, then delete only what's stale). A process interruption between the
two calls — a dropped connection, a validation error, a killed script — leaves that chapter with
zero `DialogLine` rows, and the consuming page (`.../all/page.tsx:31`) 404s, indistinguishable
from "never had a transcript." Real regression risk, not just staleness. Fix: wrap both calls in
`prisma.$transaction([...])`. Confidence: confirmed. Not P0/P1: `seed.ts` is a manually-run,
`confirmWrite`-gated script, not on any request/CI path, and fully recoverable by re-running.
**Fixed**: wrapped both calls in `prisma.$transaction([...])`.

### Security & performance (Agent E)

**5. ✅ Fixed.** **`SpeakerButton` ships both audio manifests (word + sentence, ~1,600 entries) to
every page, including ones with no audio feature — P2.** `src/components/SpeakerButton.tsx:11-12`
unconditionally imports both manifests regardless of which `kind` a given call site actually
uses. Verified via a real production build + live network trace (Playwright against `next
start`): both manifests bundle into one shared ~70KB/32KB-gzip chunk that downloads on `/login`
and `/register` — pages with zero `SpeakerButton` instances — at ~18% of `/register`'s total page
JS. Modest at this app's traffic/hosting scale, but real and easy to fix. Fix: split
`SpeakerButton` by `kind` (or lazy-load the manifest via dynamic `import()`), or move the
manifests to static JSON fetched client-side instead of bundled into JS. Confidence: confirmed
(reproduced via real build, not inferred). **Fixed**: went with the dynamic-`import()` option,
keyed by `kind`, cached at module scope so multiple `SpeakerButton`s on one page (e.g. every
`VocabTable` row) share a single load instead of each triggering its own.

**11. ✅ Fixed.** **`useQuizCountdown`'s interval effect recreates its timer every tick — P4.**
`src/quiz/use-quiz-countdown.ts:32-38`. `secondsLeft` sits in the effect's dependency array even
though the interval callback only uses the functional updater form — so React tears down and
recreates the `setInterval` once a second for the whole quiz duration instead of running one
stable interval. Negligible real cost; flagged as a genuine, cheap fix worth folding into the next
touch of this file, not urgent enough alone. **Fixed**: the interval now clears itself from
inside its own tick once exhausted, instead of depending on `secondsLeft` to trigger a recreate.
